# 威胁模型

这份文档回答一个问题：这套东西在什么前提下才算安全。它对应的是代码里已经落地的那些硬约束，不是愿望清单。

## 资产

| 资产 | 在哪 | 丢了会怎样 |
|---|---|---|
| 玩家检测数据与证据（屏幕、进程、设备指纹） | 管理后台库 + 对象存储 | 玩家隐私泄露，取证结果失去可信度 |
| PTEID 账号与信誉分 | `ptv-backend` | 冒用他人身份，检测记录被污染 |
| 玩家 token / 管理端会话 | 客户端本地 cookie、服务端会话 | 越权查端、越权解锁红屏 |
| 检测能力本身（规则、阈值、混淆产物） | `ptv-client` 发行包 | 逆向一次，后续所有检测都失效 |
| 部署密钥（JWT、WSS 签名、SMTP、飞书 SSO） | 环境变量 / Secrets | 全站凭证伪造 |
| 网关入口（四个子域） | `deploy/gateway` | 绕过限流与来源校验，直连后端 |

## 信任边界

```
玩家设备                     ｜ DMZ                 ｜ 内网
[ptv-client / 移动端探针]  →  [网关 + 限流]  →  [ptv-backend]  →  [MySQL]
        ↑                        ↑                    ↑
   物理接触者能改本机        浏览器能伪造来源      游戏服务器（明确不接入）
```

玩家设备整体视为**不可信**。这一点决定了后面所有设计：本地检测结果只作为"线索"，不作为"结论"；上送的数据必须有签名，且签名要能挡住重放。

## 逐项

### 玩家端（不可信环境）

- **伪造检测结果**：客户端可以被改，检测报告本身可以被伪造。应对是把它当线索看——管理端在采纳时结合多源证据（同一设备的多次上报、行为模型、设备指纹一致性），而不是单条报告直接定论。
- **重放上送**：WSS 消息带 HMAC-SHA256 签名、时间窗和 nonce。签名覆盖范围必须包含 payload，只盖消息头等于没盖。时间窗不能放宽到分钟级。
- **跨账号冒用**：玩家 token 的 subject 必须与 PTEID 校验绑定。这里出过一次问题的模式是"拿到别人的 token 就当自己"，所以不要在任何地方只校验 token 有效性而不校验主体。
- **本地持久化被读**：密钥与配置加密落盘。不要新增明文落盘路径，也不要把密钥写进日志。
- **产物被逆向**：发行 JAR 走 ProGuard 抹平原始包路径。这是提高成本，不是防护。真正的防护是服务端不信任客户端。
- **劫持传输**：可选证书固定，`PACC_TLS_PIN_SHA256` 同时要求系统信任链与叶证书 SPKI 指纹匹配。注意这会让证书轮换变成一次客户端更新，属于有代价的加固。

### 管理后台

- **会话被盗**：管理端 token 走 HttpOnly + Secure + SameSite 会话 cookie，不用 localStorage。会话还要绑客户端 IP 与 UA 指纹，并要求 Origin 在白名单内。绑 IP 会在移动网络下误伤，这是有意的权衡。
- **暴力破解**：登录限流按"账号 + 客户端 IP"双 key，只按 IP 会被换 IP 扫描绕过，只按账号会被撞库绕过。
- **账号枚举**：注册与登录响应不暴露账号是否存在、是否被锁。失败文案统一。
- **CSRF / 跨站请求**：靠 Origin 白名单 + SameSite cookie 双重限制。
- **越权查端**：远程查端、证据提取、解锁红屏都必须校验调用者的管理权限等级，`super-admin` 与普通管理员的边界要显式写在代码里。

### 后端与数据

- **SQL 注入 / 表达式注入**：走 JPA 与参数化查询；动态排序字段要白名单，不能直接拼。
- **日志泄露**：访问日志不记查询参数、请求头、请求体。全局异常处理对外只回通用文案，堆栈只进服务端日志。日志内容要过滤控制字符，防止日志注入。
- **敏感字段外泄**：所有对外账号数据走 `AccountView` 脱敏，密码哈希绝不能出现在任何响应里。
- **迁移误操作**：结构变更走 Flyway，生产 `ddl-auto: validate`。已合入的迁移脚本不改。
- **演示数据进生产**：`PACC_SEED` 生产必须关。

### 网关与部署

- **绕过限流**：网关按 IP 限流（普通接口 60r/m，登录注册 6r/m），并拦掉非浏览器 UA。限流放网关而不是后端，是因为后端可能被直连。
- **直连后端**：后端只信任来自网关的转发头，客户端 IP 解析优先取 `X-Forwarded-For`。
- **密钥默认值上线**：非开发 profile 下缺任意一个关键密钥就启动失败，这是有意设计——宁可起不来，也不要带着默认密钥对外服务。
- **镜像/依赖投毒**：镜像从 ghcr 拉，依赖走 Trivy 扫描；发布制品带构建来源证明。
- **发布误操作**：CD 只在打 tag 时触发，部署到 `production` 环境需人工批准。

### 仓库与供应链

- 密钥进仓库：gitleaks 扫历史 + Secret scanning + push protection。
- 依赖漏洞：Dependabot + Trivy + PR 阶段的依赖评审。
- 代码缺陷：CodeQL（`security-and-quality`）。
- action 被篡改：引用的 action 逐步 pin 到 commit SHA。
- 仓库管理姿态：OpenSSF Scorecard 每周跑，结果进 Code Scanning。

## 明确不在范围内的

- 游戏服务器侧的封禁与处罚逻辑。本系统不接入，也不提供接口。
- 已获得管理员权限的攻击者在本机上的行为。
- 玩家主动提供的假证据在物理层面的鉴别（例如别人代打）。这需要赛事侧的流程配合，不是客户端能解决的。
- 客户端运行环境被完全控制（内核级 rootkit、虚拟机整机快照）时的检测可靠性。这类场景下检测会降级为"记录异常"，而不是"给出结论"。

## 变更这份文档

新增采集项、改签名方案、放宽限流、调整权限等级——这四类改动都要同步更新这里。PR 里会被问"威胁模型更新了吗"。
